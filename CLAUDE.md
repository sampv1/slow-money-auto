# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Lọc tín hiệu is a Vietnamese stock analysis platform (paper trading only — no real trades). It started as a tracker for AI-generated daily buy/sell recommendations and has grown into a full scoring + screening system for the HOSE/HNX/UPCOM universe (~1,500+ symbols):

- **Recommendation tracking** — an AI prompt (Claude, with web search) generates daily picks; the pipeline stores them, tracks market prices, and evaluates accuracy/P&L over time.
- **Technical Analysis (TA)** — nightly compute of ~57 indicators + a TA scanner, per-stock charts, RS ratings, trend-structure scoring, S/R + trendlines.
- **Fundamental Analysis (FA)** — quarterly financials imported from FiinProX Excel, scored on a 9-criterion rubric into A/B/C bands.
- **Composite scoring** — TA Score + FA Score blended into a Final Score/grade per symbol per quarter.
- **Auxiliary signals** — VN30 futures implied risk, news sentiment/catalyst scoring, macro series.

Design docs (read these before touching a subsystem — they carry the settled decisions and formulas): `PROJECT_PLAN.md` (original phased roadmap), `TA_FEATURE_PLAN.md`, `FA_FEATURE_PLAN.md`, `PRICE_BASE_DESIGN.md`, `FA_GROUPS_DESIGN.md`, `MACRO_COMPOSITE_DESIGN.md` (the **Financial Conditions Index / FCI**, formerly "macro composite"; DB metrics `macro_fci_*` — FROZEN validation protocol, do not tune anything it freezes; the holdout was scored once and must not be re-scored). Note these docs describe intended design and may lag the code — treat the code as source of truth when they disagree.

## Architecture

Three loosely-coupled components:

1. **Python scripts** (`scripts/`) — the data pipeline. Parse Claude's JSON, push to Supabase, fetch prices via vnstock, compute TA/FA/RS/price-base/composite scores, evaluate P&L. Subpackages: `ta/` (indicators, RS, price base, S/R, trendlines, implied risk), `fa/` (Excel import, metrics, scoring, persist), `sentiment/` (catalyst scoring via Claude), `macro/`. Top-level `refresh_*.py` / `update_*.py` are the CLI/cron entry points.
2. **Supabase** — PostgreSQL with auto-generated REST API. Schema is a sequence of numbered migrations in `supabase/` (`001…041+`), applied by hand in the Supabase SQL editor. RLS: **anon is READ-ONLY** — every write needs `SUPABASE_SERVICE_ROLE_KEY`, which bypasses RLS (migration 045).
3. **Next.js dashboard** (`dashboard/`) — frontend on Vercel: recommendation views + TA/FA scanners, per-symbol analysis, implied-risk chart, admin input/import pages.

The pipeline is **DB-centric**: scripts read/write Supabase, the dashboard reads (and admin pages write) Supabase. Scripts and dashboard never call each other directly.

## Daily automation (GitHub Actions)

**A green run means the data arrived (2026-08-19).** Every daily script routes its outcome through `ta/run_status.py` and exits non-zero when a step collected nothing. This replaced the previous default, where a step's exception was printed and swallowed so one broken source could never take down the other six — right instinct, wrong default: the script still exited 0, so Actions painted the run green while the data was missing. Three runs reported **success** while collecting nothing: ta-daily on 2026-08-18 (zero bars — every vnstock call raised), macro-daily the same day (`0 vnindex`, which froze the FCI at 08-14 because the FCI's date grid *is* the VN-Index date index), and ta-daily on 2026-08-17 (29 bars of ~890).
  - **`require()` is the gate that matters, not try/except.** Wrapping a step proves nothing *raised*; it does not prove anything was *written*, and all three incidents were steps that completed cleanly and produced nothing. Steps still swallow their exceptions — the remaining steps run — but a critical one now records a failure and the process exits 1.
  - **CRITICAL vs BEST-EFFORT is a judgement about the data.** Critical (OHLCV, RS, trend, TA/Final score, every FCI input) ⇒ `::error::` + exit 1. Best-effort (catalysts on Groq's free tier, a not-yet-published CPI month, implied risk) ⇒ `::warning::` + exit 0 — still loud in the log and the job summary, because "we chose to tolerate this" must stay visible rather than silent.
  - **Legitimate emptiness is not failure**, and telling the two apart needs evidence the code did not previously keep. `fetch_latest_session` returns `failed_chunks`: a provider outage returns nothing at all (⇒ error), while a market that simply has not traded returns a session we already hold (⇒ warning). Both wrote "0 rows" on 2026-08-18 and were indistinguishable.
  - **The daily target is the market's LATEST SESSION, not `today_vn()` (2026-08-27/28).** `price_board` reports each symbol's OWN last `trading_date`, so one snapshot legitimately carries dozens of dates — the traded names share the newest session while dormant UPCOM lines still show whenever they last printed. The session is the **maximum** of those dates; older ones are other symbols' last trades, not stale data. The old guard asked `trading_date == today_vn()`, and when GitHub delayed the 09:23 UTC cron by ~10 hours the run began at **02:52 VN on the following day**, rejected a perfectly good snapshot, printed "a non-trading day … Nothing written, by design" and exited 0 — which then let the backup cron's precheck skip, because a success already existed for that day. **Two sessions were lost with every gate green.** Three questions now replace that one, each answered by whatever actually knows: *which* session (`max(trading_date)`), is it **final** (`is_session_final` — the clock, not date equality: a prior session is complete by definition, today's only after 15:00 ICT + a 15-minute settle, a future one is refused), and is it **new** (`stored_bar_count` — the DB). That clock test also closes a second latent bug: the old rule *accepted* an 11:00 intraday print as the day's close, and only the cron schedule was hiding it. `ta_runs` is stamped with the session, not the wall clock. Pinned by `scripts/tests/test_session_guard.py`.
  - **Step 1's floor is PROPORTIONAL** (`MIN_SNAPSHOT_FRACTION`, 25% of tracked members). `> 0` would have passed the 29-bar run. A normal session prices ~60-68% of members, so 25% tolerates a thin day while catching a mostly-failed collection.
  - **Freshness is not COMPLETENESS — a series can be one day old and still have a hole behind it (2026-08-19).** `interbank_overnight` is stitched from two feeds with complementary blind spots: the SBV portal is authoritative but exposes exactly ONE date (whatever it currently calls latest), while Vietstock NormID 293 carries the history and trails by 2-3 business days. A date reaches us from SBV only if our once-a-day sample lands while the portal is showing it — and on 2026-08-18 the portal read 14/08, on 2026-08-19 it read 18/08. Its own lag had shrunk from three business days to one, so **2026-08-17 was displayed to no run at all** and dropped out of the series. Every gate stayed green: the collect gate counts POINTS (a healthy 14 of them), and the staleness check reads the newest date only (2026-08-18, one day old). The FCI as-of fills its inputs, so the hole silently reused the previous session's rate. `interbank_interior_gaps` now reads back what was written and gates on the DATES — **interior gaps only** (a date missing while a LATER one is stored), because every feed here is legitimately a session or two behind daily and measuring against today would warn on a healthy series every run. The calendar comes from the stored VN-Index sessions, never Mon-Fri, so public holidays are not gaps. A detected hole also **widens the Vietstock window** to cover it, since the fixed 21-day lookback healed gaps only by luck of timing. Young gap ⇒ `::warning::` (the fallback is still catching up); older than `INTERBANK_GAP_ESCALATE_DAYS` (7) ⇒ `::error::`, because by then both feeds have published well past it. Measured before shipping: 17 interior gaps in eleven years, exactly one in the last 24 months — this check is not a source of routine noise. `audit_data.py` reports the same for the VN-calendar series (`VN_CALENDAR_DAILY`; sofr/dxy/govbond are deliberately excluded — they follow other calendars and would show 7-9 phantom gaps a year each). Pinned by `scripts/tests/test_interbank_gaps.py`.
  - **The FCI is gated on FRESHNESS, not row count** (`FCI_MAX_SESSIONS_BEHIND`, 1). `compute_fci_rows` rewrites a trailing slice, so it happily returns hundreds of rows whose newest date is days old — the 2026-08-18 run wrote 270 FCI rows and still ended at 08-14. Only the latest date proves the grid advanced.
  - **A CLOSED MARKET IS NOT A STALE PIPELINE (2026-09-01).** That gate first allowed 4 CALENDAR days, which cannot tell the two apart: the FCI grid IS the VN-Index date index, so during a closure the newest FCI date is correct and unchanging while the calendar keeps moving. Measured over 1,911 sessions since 2019: **22 closures exceed four days, ~2.9 a year**, and **Tết turns the run red for three consecutive days every year** (2023-01-24/25/26, 2024-02-12/13/14, 2025-01-29/30/31, 2026-02-18/19/20); the 2026 National Day closure (08-31…09-02) would have added another. The gate now counts stored VN-Index **sessions** the FCI trails (`fci_sessions_behind`) — a closure produces none, a genuinely stuck FCI falls behind sessions that exist. A vnindex collection failure is caught separately by its own `require`, so the two gates do not overlap. The threshold is an operational monitor, **not** part of the frozen FCI protocol (W=504 / DXY-level / the consumed holdout), and cannot move a score. Same lesson as the daily session guard: ask the market what day it is, not the clock.
  - **Holidays are not sessions, and `update_prices.py` was counting them** (fixed 2026-09-01). `count_business_days` counted Mon–Fri with no holiday calendar, so each closed weekday aged a position by one. That feeds `check_expiry`, which runs **even when there is no fresh bar** (`elif not updates:`), so a position could be marked `EXPIRED` with `closed_at` stamped on a day the market never opened; it also feeds the T+2.5 settlement test, where phantom sessions make a position look settled early. `count_sessions_held` now counts real sessions from `macro_series.vnindex` — one row per session, the same calendar `interbank_interior_gaps` already trusts (`ta_ohlcv` answers the same question but holds ~900 rows per date). Measured on AIG at 2026-09-02: Mon–Fri says 24, real sessions 21. A failed calendar read falls back to Mon–Fri rather than refusing to age a position. It was latent when found — all five open positions had `holding_period_sessions = 0`. Both pinned by `scripts/tests/test_holiday_gates.py`.
  - **A red primary now triggers the backup cron.** `ta-daily.yml`'s backup skips only if an earlier run *succeeded*; with success redefined, a data outage gets an automatic retry it never used to get.
  - **The VN-Index has a provider chain** (`BENCHMARK_SOURCES`: VCI → KBS → MSN, then `macro_series` for TA readers). One fetch broke two pipelines on 2026-08-18; a series this load-bearing should not have a single point of failure. All three verified to return the same close for the same session. TCBS is deliberately absent — vnstock 4.x rejects it for `Quote`. Pinned by `scripts/tests/test_run_status.py`.

Cron workflows in `.github/workflows/` (times in UTC; VN market closes ~07:45 UTC). Each expects `SUPABASE_URL` / `SUPABASE_ANON_KEY` (and some `ANTHROPIC_API_KEY`) as secrets.

**Catalysts run best-effort on Groq's free tier and will NOT score every symbol every night.** `groq/compound` returns HTTP 413 on ~9 of 10 calls. This is not a request-size problem and is not worth re-diagnosing: the failure arrives 15–22 s in (*after* its search loop ran), the same prompt on a plain model answers in 1.5 s, shrinking the prompt or `max_tokens` doesn't help, and it fires while the visible budget still reads ~69,000/70,000 tokens. A 429 named the true ceiling — `meta-llama/llama-4-scout`, the sub-model compound drives its search loop with, which **404s if called directly** and therefore has a quota that is invisible in the response headers and untunable from the request. `_score_one` retries with **spacing**; do not make retries rapid — 12 attempts 8 s apart drained that sub-model's quota and turned every 413 into a 429, strictly worse. A symbol that never lands returns `None` and keeps its previous score, so coverage accumulates across nights instead of being wiped. A paid Groq tier is what would make this deterministic.

## Scoring pipeline

The composite score is built bottom-up; each formula lives in the code, not just the docs:

- **FA Score** (`fa/scoring.py`) — 9 criteria, graduated 0/4/8/12 pts (debt can be −4), max 108, YoY growth. Bands: A ≥ 60, B ≥ 30, C < 30, else UNRATED (banks/securities lack margins). Tiers are data-driven from the `fa_scoring_config` DB row (seeded by migration, edited directly in DB — no import path; forward-only, no retroactive rescore). Stored per (symbol, quarter) in `fa_scores`, normalized to 0–100.
- **RS Ratings** (`ta/rs_rating.py`, `refresh_rs.py`) — cross-sectional 1–99 percentiles of trailing 3/6/9/12-month return + weighted composite. Written onto `ta_universe`. `rs_1m` is a fifth, **display-only** percentile (FA Scanner) computed in a separate pass **outside** the composite blend — never add `"1m"` to `periods`/`weights`: `blend` indexes `weights[k]` for every `k` in `periods` (so a missing weight is a `KeyError` that writes no RS at all), `_deep_merge` preserves nested code defaults so the `scoring_config` row does **not** protect you, and any real weight would move `rs_composite` → TA Score → Final Score for every symbol. Pinned by `scripts/tests/test_rs_periods_weights.py`.
  - **Each period is gated on its own data** (`_trailing_returns(..., require_all=False)`, 2026-08-11). A symbol is ranked for `rs_3m` if it has a bar within `tolerance_days` of the 3-month mark, regardless of its 12-month anchor — so the `rs_3m`/`6m`/`9m`/`12m` populations differ and any of them can be null on a row. `rs_composite` still requires **all four**, keeping TA Score and Final Score a blend of four real numbers. Previously one missing anchor voided the whole symbol, costing ~60 symbols their `rs_3m` for want of 12-month data the 3-month return never uses (and "missing" usually meant a *hole* at the anchor, not a young listing — AMV had 230 bars over 777 days). Pinned by `scripts/tests/test_rs_per_period_gate.py`.
  - **The RS Line fails CLOSED on a missing benchmark (2026-08-18).** RS Line = close ÷ VN-Index, so no VN-Index means no RS Line for *anybody*. The write path used to send `rs_line*: None` for all 1,422 rated symbols in that case, and since TA Score weights `rs_line_score` at 20% and scores a **missing component as 0**, one flaky external call marked down the TA Score, Final Score and grade of the entire universe — mean −8.5 points, max −20. Now the payload **omits** the `rs_line*` keys when there is no benchmark (an upsert leaves unnamed columns alone), so the prior snapshot survives; a symbol that has a benchmark but too little data of its own still gets a genuine null. Absence of the yardstick is not evidence that 1,400 stocks lost their relative strength.
  - **The benchmark has a DB fallback: `get_vnindex_closes(client)`, not `fetch_vnindex_closes()`.** vnstock raised `RetryError[UnboundLocalError]` twice 84 minutes apart on 2026-08-18, too long for a retry loop to rescue — but `macro_series.vnindex` already carries 5,600+ daily closes written by `macro-daily.yml`. The TA pipeline reads live-then-DB; **`refresh_macro.py` must keep using the raw `fetch_vnindex_closes`**, since it is what populates that DB copy and must never read back its own output. Both pinned by `scripts/tests/test_rs_line_benchmark_outage.py`.
  - **`pct()` must coerce to numpy `float` before `rank()`.** On pandas' *nullable* dtypes (`Int64`/`Float64`) `rank()` does not honour `na_option="keep"` — it hands `pd.NA` a real rank (measured on 2.3.3: `[30.0, <NA>, 59.4]` → `[66, 33, 99]`). That fabricated an `rs_composite` for 99 partially-rated symbols on the first cut of the per-period gate. Asserting on the blend alone does not catch it; the null is resurrected one step later, inside the ranking.
- **FA Score — real estate** (`fa/real_estate.py`, `refresh_fa_re.py`) — property developers are scored on their OWN 13-criterion rubric, max 100, defined in `data/tieu_chi_cham_diem_bds.xlsx` (weights + bands are READ FROM THE SHEET, never hard-coded). It sees what the manufacturing rubric cannot: land bank (`tồn kho tổng` = inventory **+ chi phí SXKD dở dang dài hạn**, which for some names is the larger half), customer advances (`người mua trả tiền trước`), and cash flow. Stored in `fa_re_scores` with a jsonb `breakdown`, so adding or redefining a criterion needs no migration.
  - **Raw inputs are stored separately** in `fa_re_metrics`, so a rubric edit re-scores from the DB — `refresh_fa_re.py score` alone, no re-export. The rubric changed four times in two days; this split is why that costs one command.
  - **Two precedence rules override the bands.** Zero borrowings ⇒ maximum on C4/C6/C8 (no debt is the unambiguous best case). C10 is deliberately NOT in that set: it tests cash flow FIRST — `CFO TTM ≤ 0` scores 0 whatever the debt is — so a debt-free company burning cash does not collect a free 8. A symbol that filed NOTHING has blank debt columns, which is absence of data, not absence of debt, and gets neither.
  - **No normalization (2026-08-14).** The weights sum to exactly 100, so the raw total IS the 0-100 score; a criterion with a missing input scores nothing (not zero) and the symbol simply ends up with fewer points. `normalized_score` mirrors `total_score` and is NULL only when NOTHING could be scored (21 symbols filed no Q2/2026 balance sheet) — that is absence of data, not a zero, so the Final Score skips them.

- **FA statements — vnstock** (`fa/vnstock_source.py`, `refresh_fa_vnstock.py`) — the full income / balance / cash-flow / ratio statements for ~1,750 symbols, quarterly and annual, stored as jsonb in `fa_vnstock_statements` (migration 055). This is the **Analysis page's nine financial charts only**; it feeds no score, and is deliberately SEPARATE from the FiinProX tables so the two sources can never be mixed in one number — their EPS diverges materially (as-filed 0.0 for HPG/SSI, −33.3% for PNJ) even though revenue / gross profit / NPAT / equity / debt agree to 0.00%.
  - **jsonb, not one row per metric.** 1,750 symbols × 34 periods × ~100 metrics is 5.4M long-form rows against ~240k bucketed by (symbol, period, period_type, statement). ABSENT is never written as 0 — a category header row carries no value and simply never enters `items`.
  - **A FAILED CALL AND AN UNPUBLISHED STATEMENT ARE NOT THE SAME THING (2026-08-30).** `fetch_symbol` wrapped each provider call in `try/except: continue`, so a call that *raised* and a statement the provider genuinely does not publish both ended as "no rows". A transient network failure therefore cost a symbol a whole statement while the run printed `ok` and exited 0 — VNM lost its entire quarterly balance sheet (0 rows against FPT's 34), which is exactly charts 7, 8 and 9, while re-fetching it directly returned 4,012 rows. Auditing all eight statement/period combinations per symbol found **625 of 1,734 missing at least one**; re-fetching recovered 197, so the failure is per-CALL and transient. Each statement is now attempted 3× with a widening pause, `fetch_symbol` returns a failed-call COUNT, and a symbol with any failed call is reported `partial` rather than `ok` — with a ready-to-paste `--symbols` re-run list. Same rule as the daily pipeline: legitimate emptiness is not failure, and telling the two apart needs evidence the code did not previously keep.
  - **An exhausted retry must not end the run.** `safe_execute` already retries the write and correctly classes DNS failure as transient, but its backoff spans ~7s, so a longer outage re-raises — and that exception escaped the loop, killing the backfill at symbol 717 of 1,751. The write is now guarded per symbol. `socket.gaierror` was added to `_TRANSIENT_ERROR_TYPES` for the bare case.
  - **`--resume` skips any symbol with ANY rows**, so it cannot repair a partial symbol — use `--symbols` for that. Upserts are idempotent, so re-running is always safe.
  - **The script does NOT revalidate the dashboard cache.** Unlike the cron workflows it is run by hand, so a load must be followed by `curl -X POST -H "x-revalidate-secret: $REVALIDATE_SECRET" "https://www.loctinhieu.com/api/revalidate?tags=fa-data"` or the pages keep serving the empty cached read.
  - **The nine charts encode a NON-FINANCIAL balance sheet.** Banks and securities firms file different formats, so the named line items are absent: the residual "Khác" is 98% of TCB's total assets and 90% of VND's. Charts 7 and 8 refuse to draw above a 50% residual (`residualKey` / `DEFAULT_RESIDUAL_LIMIT`) rather than assert that a bank holds a million tỷ of unclassified assets. TCB keeps 4 of 9 cards, VND 8. A proper bank set would be its own `ChartSpec` array — the provider already ships 15 unused `RT_BANK_*` ratios per quarter.
  - **Chart 6's P/E and P/B come from the provider, with only the newest point recomputed.** `ta_ohlcv` and vnstock agree to the đồng but are TOTAL-RETURN back-adjusted (bonus shares AND cash dividends), so pairing them with an as-reported share count misprices history by −37% to +26% — the tell being that the P/E error and the P/B error are IDENTICAL every quarter, i.e. the fault is entirely in the price. At the right edge the adjusted close IS the traded close, so the current quarter is marked to `ta_ohlcv`'s latest bar and the readout names its date. The provider's own ANNUAL ratio row is unusable (FPT 2023: P/E 29.96 vs the Q4 row's 22.64; its implied 2021 BVPS exceeds total equity per share), so the annual layer reads the Q4 quarterly row.

- **Trend Score** (`ta/trend_score.py`, `ta/zigzag.py`, `refresh_trend.py`) — `Daily·60% + Weekly·40%`, both 0–100, per `data/He_thong_cham_diem_Xu_huong_TA_Pro_Bo_sung.xlsx` (migration 051). Both halves read the **same structure** off a ZigZag over ~1.5 years — **daily 5% / 3 candles, weekly 7% / 6**, deliberately not the same settings (10 *weekly* candles is a 10-week minimum between pivots in a window holding only ~78 of them, which left 40% of the universe with one weekly pivot and 3 symbols of 1,158 able to complete a weekly uptrend; 7%/6 took that to 607 and 10): `O` the last lower-high before the bottom, `K` the bottom, `A` the close that takes O back out, `D1` the first pullback, `A1` a close back above A. Weekly is the same machine **one leg behind** — its A1 is daily's A and its A2 is daily's A1, which is why weekly needs an extra leg to reach 100.
  - **The state table beats the arithmetic.** Daily D1 scores **60, the same as A, not 70** — the spec says so twice; TC4's 10 points only land at A1, where 15+15+30+10+30 = 100. Weekly does add them at D1 (15+15+40+10 = 80).
  - **A failing base condition caps everything.** TC1 (within −25% of the 52-week high) and TC2 (close > daily MA200) are worth 15 each; if either fails the score falls back to what those two earn alone, however complete the structure. Weekly is stricter still: below the daily MA200 the score is **0, ahead of every other rule** — which on 2026-08-17 was 792 of 1,158 scored symbols, an independently verified market condition, not an artifact.
  - **TC1 and TC2 are the same test on both timeframes**, because the in-progress week's close IS the latest daily close. The halves differ only in the structure.
  - **The ZigZag seeds its first leg at bar 0**, so a symbol whose window opens below its later lows produces a bar-0 "trough" no peak can precede. Recording that as K would pin it at the window's cheapest price forever and reject every genuine O–K pair formed later as "higher" — the symbol reads no-structure for good. Such troughs are skipped, not recorded (124 symbols hit this; 117 with the trough inside the first ten bars). Pinned by `scripts/tests/test_trend_score.py`.
  - **The row shows a direction, not a score.** Each half's 0–100 maps to one of five arrows through `direction_bands`, whose thresholds ARE the state table's own score levels (100 / 60 / 30 / 15 / 0), so an arrow can never contradict the state that produced it. The columns still sort on the number — five values would sort into five indistinguishable blocks.
  - **Trạng thái and Hành động come from the DAILY state alone** (`_verdict`, one map each), per the customer's UI prototype, which pairs a "Sẵn sàng mua" with a falling weekly column. Four statuses — `tao_day` (O–K base) · `san_sang_mua` (a close just took out a level) · `cho_mua` (pulled back and holding) · `tiep_dien` (uptrend intact, no fresh break) — and NULL for anything else, which is 79% of the universe. The weekly chart still constrains this indirectly: a status only exists for daily states that passed BOTH base conditions, so nothing below the MA200 can reach a buy. Action is a pure function of status, and encodes that a stock already deep in an uptrend reads **Theo dõi**, not a buy — entries are on a breakout or after a healthy correction.
  - **State labels are the customer's naming (2026-08-17), and one of them is a real distinction, not wording.** `Xu hướng tăng xác nhận` is a fresh completion (`a1_uptrend` / `a2_full_uptrend` — one higher high); `Xu hướng tăng mạnh` is the same structure *after* a trough has confirmed above the reset level (`post_a1_above_d1` / `d2_above_a1` — higher high AND higher low). That is the HH/HL half of the customer's definition; the momentum-agreement half is not computed, so the label rests on structure alone. The four weak states share one label (`Xu hướng yếu`) deliberately: `ok_below_ma200` (daily) and `below_ma200` (weekly) are the SAME price test, so distinct wording made a row contradict itself. Labels live in `trend.tsx` typed `Record<TrendState, …>`, so adding a state in Python without a label is a compile error — the homepage's inlined copy shipped with stale codes once and rendered a dash on every row.
  - **BỔ SUNG 01 re-seats O/K on sideways chop around the MA200 (2026-08-19).** The base rule makes K the *lowest* trough of the decline, which on a stock that chops across its MA200 anchors the structure on whichever dip was cheapest — often months stale. BIO and CSM were both still anchored on a K from 2025-04-22, sixteen months old, while price had long since recovered. So when price is back above the MA200 **and** at least 3 ZigZag lows sat below the MA200 **of their own day** inside 52 weeks, O/K re-seat on the **most recent** such low (`sideway_reset` in `TREND_DEFAULTS`). The spec says twice that this is by DATE, not price — "chọn ĐÁY DƯỚI MA200 CUỐI CÙNG theo thời gian, KHÔNG chọn đáy có giá thấp nhất 52W". Three things it deliberately does NOT do: touch any score or state (it only moves where the structure starts), run on the weekly chart ("Chỉ áp dụng cho Trend ngày"), or fire before K is confirmed — the re-seat lands on K's confirmation bar, because seeding it earlier would let the walk compare closes against an O that had not formed yet. Rare by design: 4 of 402 sampled symbols reach N≥3, and only ~30% pass the above-MA200 gate at all. Pinned by `scripts/tests/test_trend_sideway_reset.py`.
  - **Too little history returns NULL, not 0** (`min_bars` 200): without MA200 neither TC2 nor the weekly hard rule can be evaluated, and absence of data is not a failed test. 273 of 1,431 active symbols are sparse enough to fall here.
  - **`ta_ohlcv` is raw and unadjusted, and this module walks 1.5 years of it** — far more exposed than BQS, which only looked at a few recent weeks. 473 of 1,158 symbols carry at least one single-day drop beyond any exchange's band, i.e. an unrepaired corporate action that manufactures a fake K or a fake break. Run `refresh_adjustments.py --scan-days 560` before trusting a first run.
- **S/R levels** (`ta/sr.py`) — swing pivots clustered within `0.5 × ATR`, scored `touches × 0.95^days_since_touch`, top 5 per side written to `ta_sr_levels` nightly (overwritten, not upserted — levels drift, and `price` is the key).
  - **The recency decay underflowed the price, not just the score (fixed 2026-09-02).** `0.95^days` reaches 4.3e-14 by 600 bars, and the cluster price divided by the raw sum of those weights under a `max(den, 1e-9)` divide-by-zero guard. For **any cluster whose pivots are all older than ~404 bars** that sum is legitimately below the floor, so the guard divided a tiny numerator by a much larger constant and rescaled the price by orders of magnitude — DIG carrying a "support" at **0.0166** on a series whose low is 2.32, PVH four levels between 4.8 and 122 against a 500–3100 range, CAN levels at 99–1,107 against a 14,156 median. **713 impossible levels across 419 symbols — 28% of the universe — live when found**, drawn on charts and feeding `near_support` / `rejects_at_resistance` / `wyckoff_spring`. The fix shifts the decay exponent by the cluster's own newest pivot, which cancels out of the ratio: same weighted mean, denominator now ≥ 1.0 by construction, no floor needed. `strength` is scaled back to the absolute scale so cluster ranking is unchanged — and it may collapse to ~1e-88 for an ancient cluster, which is correct, since it only orders. Recomputing 60 random symbols moved the level set on **60%** (more than the 28% that held a bad level, because freeing a `KEEP_PER_SIDE` slot lets a real level in) and left 0 out-of-range. Pinned by `scripts/tests/test_sr_cluster_underflow.py`.
  - **`detect_levels` has NO window of its own** — it scans whatever DataFrame it is handed, unlike `detect_trendlines` (`LOOKBACK_BARS = 90`). It is fed by `compute_ta_signals.load_ohlcv`, so the depth of `ta_ohlcv` silently sets the depth of S/R detection. That is why bounding `load_ohlcv` is the precondition for any deeper OHLCV backfill: without it a full-history table would re-seat S/R levels for the whole universe.
- **Price Base / BQS** (`ta/price_base.py`, `refresh_base.py`) — **RETIRED 2026-08-17**, replaced by the Trend Score. Out of the daily pass, out of TA Score, off Signal Pro and the homepage. The module, its tests and the `base_*` columns all survive (migrations are append-only), so what those columns hold is a **snapshot frozen on the retirement date** — the columns carry `COMMENT`s saying so. Scored 0–100 per the **BQS V8** rubric (`supabase/033_bqs_v8.sql`, `PRICE_BASE_DESIGN.md`).
- **TA Score** (`ta/ta_score.py`, `refresh_ta_score.py`) — `RS3M·20% + RS Composite·20% + RS Line·20% + Trend·40%` (missing component = 0, migration **052**). Trend's 40% is BQS's old 35% (migration 051) plus 5 points taken from RS Composite — a trim that removes a real overlap rather than de-weighting relative strength, since `rs_3m` is itself one of the four periods blended into `rs_composite`, so the two were counting the 3-month return twice. **That migration must be applied**, not just the code deployed: `load_scoring_config` deep-merges the stored row over the code defaults, so a row still holding `"bqs": 0.35` keeps it alongside the new `"trend": 0.35` and the weights sum to **1.35**. `_resolve_weights` drops orphan keys with a `::warning::` rather than raising, so the gap between deploy and migration produces correct scores loudly instead of inflated ones silently.
- **Final Score** (`ta/final_score.py`, `refresh_final_score.py`) — `0.59·TA + 0.41·FA` (both 0–100), written per quarter onto `fa_scores`; only the latest period is (re)written, older quarters stay frozen. **The FA half is rubric-aware:** a symbol in `fa_industry` with `industry_group='real_estate'` takes its FA score from `fa_re_scores`, not `fa_scores`. A real-estate symbol with no usable RE score gets NO Final Score rather than falling back to its stale manufacturing number — otherwise one column would mean two different things depending on the row.

**Universes are SEPARATE (2026-08-11).** TA and FA each own their symbol set; **Final Score is the inner join** — it's written per `(symbol, as_of_period)` onto `fa_scores`, so a TA-only symbol never receives one and an FA-only symbol keeps its FA score with no technical read. Neither side caps the other.

- **TA universe ← the exchange's stock listing.** `refresh_ta_universe.py --source listing` (the default) syncs `ta_universe` to vnstock's `type='stock'` roster for HOSE/HNX/UPCOM (~1,525). A failed listing fetch writes **nothing** — one flaky external call must never read as "everything is delisted".
- **`is_active` ⟺ listed as a stock AND traded within `--stale-days` (90).** One predicate, one owner (`sync_universe_to_listing`). Splitting it across two commands makes them undo each other — membership reactivates what liveness just retired — so both halves are applied in a single pass. `refresh_ta_universe.py --retire-stale` applies the liveness half alone for a cheap daily pass. Retiring also **blanks the derived reads** (`RETIRED_FIELDS`: every `rs_*`, plus `ta_score`), because only two dashboard reads filter on `is_active`, so a retired row left holding `rs_3m` stays visible everywhere else.
- **Collection is wider than scoring.** `update_ta_daily.py` Step 1 fetches OHLCV for **all members** (`get_universe_symbols`); everything that ranks or displays uses `get_active_symbols`. Collecting only the active set makes dormancy unobservable for anything excluded — `excluded ⇒ no data ⇒ looks dormant ⇒ stays excluded` — a loop no re-sync can open. It had already closed on 14 listed, tradeable stocks whose bars stop dead on two dates that are FA-alignment runs, not delistings. Step 1 is one bulk `price_board` snapshot, so the extra members cost ~nothing.
- **`--source fa` is DEPRECATED** and warns loudly. It derived `ta_universe` from `fa_scores`, so a symbol was scanned technically only if someone had imported its financials from a FiinProX spreadsheet — though TA needs nothing but OHLCV. It also can't tell a fund from a stock (20 ETFs incl. `E1VFVN30` and the `FUE*` family were being percentile-ranked against ordinary shares) nor a delisting from a new listing.
- `is_active` means "tracked," not "liquid" — **liquidity is a view-time filter** on the scanners (default 200k avg 20-session volume), never applied to `is_active`.

**After a sync that adds symbols:** `backfill_ta_ohlcv.py --symbols …`, then `refresh_rs.py` → `refresh_ta_score.py` → `refresh_final_score.py`. RS is cross-sectional, so changing membership moves every percentile.

**Daily OHLCV:** `update_ta_daily.py` Step 1 fetches the market's latest completed session for the whole universe via vnstock `Trading.price_board` (bulk, ~seconds; see the session guard above — the target is the newest `trading_date` the snapshot carries, gated on being final and not already stored). `history()` is the **backfill / gap-fill** path only (`backfill_ta_ohlcv.py`), not the daily run. Signals must never use data past the target date (lookahead bias — critical for backfill correctness).

**Price adjustments (unadjusted-history bug):** `ta_ohlcv` is **append-only and stores RAW, UNADJUSTED prices** — price_board appends today's raw bar and never re-adjusts older ones, while `history()` returns a **back-adjusted** series. So a corporate action (dividend/rights/bonus/split) leaves a discontinuity at the ex-date that corrupts trailing returns and RS (it was the main cause of RS3M divergence vs adjusted sources like Fialda). `update_ta_daily.py` **Step 1b** (`ta/adjustments.py`) detects just-adjusted symbols — impossible day-over-day gap beyond the exchange limit (any exchange) + `ref_price` ≠ stored prior close (HOSE/HNX only; UPCOM's reference is an average) — and re-backfills **only those** with adjusted `history()` (verify-and-skip, so genuine crashes are no-ops). The daily pass (scan_days=15) self-heals new actions; clean up existing/older corruption once with `refresh_adjustments.py --scan-days 450` then `refresh_rs.py`.

## Data flow (recommendation tracking)

**Manual:** run a trading prompt (`prompts/prompt-trading-vietnam-*.md`, latest is v7.3) in Claude with web search → Claude outputs full analysis + a `json` code block → copy JSON → `push_recommendation.py` → Supabase. Prompts are versioned in `prompts/`; both a `-complete` (analysis) and `-json` (with output block) variant exist per version.

**Automated:** `run_prompt.py` sends the prompt to the Claude API with web search enabled, extracts the JSON, and pushes it. Full responses are saved to `scripts/outputs/`.

**Evaluation:** after market close, `update_prices.py` fetches closing prices, checks TP1/TP2/SL, and updates status + P&L.

## JSON schema (trading prompt output)

A JSON object with: `analysis_date`, `trading_date`, `market_context` (regime 1–4, auction state, VN-Index, international data), `conclusion` (KB1/KB2/KB3), `recommendations[]` (symbol, entry/SL/TP prices, stats), `scenarios`, `track_record`. Examples: `scripts/sample_kb1.json`, `scripts/sample_kb3.json`, `scripts/sample_real_2204.json`.

## Database tables

Core: `daily_logs` (one row per trading day) + `recommendations` (individual picks with tracking status). TA: `ta_universe` (per-symbol snapshot: RS, base, TA/Final scores, avg volume), `ta_ohlcv`, `ta_signals`, `ta_runs`, `ta_sr_levels`, `ta_trendlines`. FA: `fa_quarterly`, `fa_annual_pe`, `fa_scores` (keyed `(symbol, as_of_period)` — full quarterly history), `fa_scoring_config`, plus the real-estate set `fa_industry` (which rubric a symbol belongs to), `fa_re_metrics` (raw inputs) and `fa_re_scores` (migration 048), and the chart-only vnstock set `fa_vnstock_statements` + `fa_vnstock_metrics` (migration 055). Reference: `symbol_profile` (company name + ICB L1–L4 codes + company type + logo, per symbol) and `icb_sectors` (bilingual labels, keyed `(icb_code, level)`) — migration 050. Others: `profiles` (roles), `feedbacks`, `implied_risk`, `symbol_catalysts`, `macro_series`, `scoring_config`. Full definitions in the numbered `supabase/*.sql` migrations.

**Company name + industry sector** (`ta/profile.py`, `refresh_symbol_profile.py`, Step 7 of the daily pass) come from ONE keyless call to Vietcap's `search-bar` endpoint, per language — 2,092 companies in under a second, 100% coverage of name/short name/company type/ICB L1–L4 across the active universe in **both** vi and en (`logo_url` is only 71%, so every read must tolerate null). Two things it must keep doing:
  - **Fail closed.** Either language failing, an empty payload, or zero parsed symbols all return `None` and write NOTHING. The tables are upserted and never truncated, so a partial fetch would overwrite good rows with nulls that the next run cannot distinguish from companies that genuinely lack an English name — and an empty result would upsert 0 rows, print "0 symbols" and exit 0, which reads exactly like success.
  - **Resolve ticker collisions by rank, not by dict order.** The payload repeats codes: `VNH` is both `CTCP Đầu tư Việt Việt Nhật` (UPCOM, an ordinary company — ours) and `Vietnam Holding Ltd` (floor `OTHER`, a foreign fund). The obvious `{r["code"]: r for r in data}` keeps the LAST record and filed our UPCOM stock under `Quỹ đầu tư`; `_rank` prefers a real exchange, then a non-fund. Both pinned by `scripts/tests/test_symbol_profile.py`.
  - **`fa_industry` is NOT touched.** It stays FiinProX-authoritative so the real-estate FA rubric split cannot move — `symbol_profile` is additive reference data with no reader in the pipeline. The two agree independently: VCI's ICB L4 matches `fa_industry.icb_industry` on 1,588/1,592 (99.7%) and all 118 real-estate symbols land at L2 `8600 Bất động sản`.
  - **ICB L1 is not the grouping a reader expects.** ICB files real estate under Financials, so 120 of the 181 active symbols at L1 `8000` are property developers; the source also injects a custom L1 `8301 Ngân hàng` whose code sits in the L2 numeric range (hence the `(icb_code, level)` key). L2 or L4 are the honest choices for a sector filter. Codes are zero-padded text (`0001`, `0533`) — coercing them to int breaks the join.

## Key conventions

- Recommendation status lifecycle: `OPEN → TP1_HIT → TP2_HIT` | `OPEN → STOPPED` | `OPEN → EXPIRED` | `OPEN → CLOSED_MANUAL`.
- KB1 = recommendations available, KB2 = cautious, KB3 = stand aside (empty `recommendations`).
- Prices in VND, percentages as floats (`5.5` = 5.5%), dates `YYYY-MM-DD`. `daily_logs.trading_date` is unique — one analysis per day.
- Stock data via vnstock (KBS/VCI sources; free tier ~20 req/min guest, 60 registered). Sequential fetches use a 3.5s delay; the daily OHLCV path uses bulk `price_board` instead.
- **`vnstock` is PINNED to `==4.0.4` and must not be loosened.** 4.0.5+ ship a `get_hosting_service()` (`vnstock/core/utils/env.py`) that is an if/elif chain with **no else**: every branch tests a cloud-host env var, so on an ordinary machine none match and `return hosting_service` reads a name never bound. 4.0.4 survives only by accident — its last branch subscripts `os.environ["SPACE_HOST"]` unguarded and the resulting `KeyError` is swallowed by a bare `except` that assigns the variable, so the **error path is the assignment** (set `SPACE_HOST` to any non-HF value and 4.0.4 raises too). 4.0.5 "fixed" that `KeyError` by guarding the lookup, which deleted the accidental assignment and made the `UnboundLocalError` unconditional; 4.0.6 then called it from `send_request()` on the VCI path, so **every request raises**. On 2026-08-18 the requirement read `>=3.4.0`, CI installed fresh, resolved to 4.0.6, and the pipeline collected **zero bars** — `price_board`, `history` and the benchmark all failing as `RetryError[UnboundLocalError]`, which tenacity's repr renders without the message, hiding the cause. `ta.common.patch_vnstock_hosting_service()` repairs the function at import time as a second line of defence. Both pinned by `scripts/tests/test_vnstock_hosting_patch.py`; remove them only once upstream ships a real `else`.
- P&L: when both TP1 and TP2 exist, assume 50% exits at each; blended P&L = average of both gains. After TP1 hit, SL moves to entry (breakeven).
- Vietnam T+2.5 settlement: SL/TP checks apply only from T+3 onward; before that, price is updated but no exit triggers.
- Corporate-action rebase (`update_prices.py`): vnstock KBS returns BACK-ADJUSTED prices, but a recommendation's entry/SL/TP are the NOMINAL levels captured at rec time. Each eval computes `k = adjusted_close(last_close_date) / last_close` and divides today's fetched OHLC by `k` (rebasing it to the rec's nominal basis) so a dividend/bonus ex-date drop can't false-trigger a stop. `k=1` (no rebase) when there's no reference or `|k−1| ≤ 1%`.
  - **`k` comes from three witnesses combined with `min()`, not from the provider alone** (`effective_factor`). Over a position's life `k` is **monotonically non-increasing** — the denominator is fixed at rec time and every corporate action only lowers the numerator — so a source that is behind reports `k` too HIGH (1.0 = "nothing happened"), never too low. Every failure mode biases one way, which makes the lowest candidate the best-informed one and a *rise* in `k` a source regressing, never an action reversing. The witnesses: the provider's `history()`; `recommendations.adj_factor`, persisted by an earlier run; and `ta_ohlcv`, which the TA pipeline re-backfills adjusted in its Step 1b.
  - **Two guards, covering different sessions.** `SUSPECT_REF_DEV` defers an exit when the exchange reference disagrees with our last stored close — but that signal only exists ON the ex-date, because the reference is reset to the adjusted close overnight. From ex-date+1 the extra witnesses above are what stand in. AIG was stopped twice for one 15% bonus (ex 2026-08-04): once on the ex-date, then again on 08-05 when its 46,900 low was measured against a pre-bonus 48,000 stop and booked as −5.88% on a position that was up ~7%. Its correct factor (0.860962) was already on the row AND in `ta_ohlcv`; the run consulted neither. Pinned by `scripts/tests/test_adjustment_factor.py`.
  - **`k > 1` is rejected** (`_sane_factor`). No corporate action raises the adjusted price, so a ratio above 1 is a mistyped manual `last_close` or a provider glitch — and since the rebase *divides* by `k`, leaving it marks every price down and fires the same false stop with the sign flipped.
  - **Open positions are repaired unconditionally** in `update_ta_daily.py` Step 1b, not only when a detector flags them. `find_gap` needs a move beyond the exchange band (UPCOM: 15% + 3%) and the reference check is disabled on UPCOM entirely (its reference is a session average), so **a UPCOM action under ~18% is invisible to both** — AIG's bonus moved the price −13.0% and was caught by neither, leaving its history unadjusted until a hand-run repair. `repair_symbols` verifies and skips, so an already-correct symbol costs one `history()` call and writes nothing. `detect_restated` remains the reliable detector for a full sweep (`refresh_adjustments.py --restate`); it is not in the daily pass because it costs one call per symbol.
- Expiry: recommendations auto-expire after 1.5× their `holding_period_sessions`.
- Excel imports (FA) are **additive per-row UPSERTs of only the rows present** — partial files, re-importable, never truncate. FA growth is **YoY**; inputs are single-quarter except ROE (TTM).
- **The FA Scanner is split by rubric.** `/fa-scanner` redirects to `/fa-scanner/manufacturing`; `/fa-scanner/real-estate` is the BĐS rubric. Each symbol appears on exactly ONE tab — the manufacturing page subtracts `fa_industry.industry_group='real_estate'`, because a property developer still carries a stale manufacturing row in `fa_scores` and showing it would give one company two unrelated scores on two tabs. Both pages degrade to the pre-migration behaviour if 048 is not applied. **`industry_group` is a BINARY split (2026-08-14):** `real_estate` is exactly `Phân ngành - ICB L4 == "Bất động sản"` (118 symbols); everything else is `manufacturing`, construction and financials included. `fa_industry`'s check constraint still permits `construction`/`financial` for when those rubrics land, but nothing emits them — a group value with no rubric behind it only invites the manufacturing page to subtract symbols into a page that does not exist.
- Dashboard is bilingual (en/vi) via `dashboard/src/lib/i18n.ts`; TA indicator specs are mirrored between Python (`scripts/ta/registry.py`) and TS (`dashboard/src/lib/ta-indicators.ts`) — keep them in sync when adding indicators.
- **Dashboard data cache:** public-page Supabase reads are wrapped in `unstable_cache` (`dashboard/src/lib/cached-data.ts`) tagged `ta-data` / `fa-data` / `macro-data` (1 h TTL safety net). Freshness is event-driven: each pipeline workflow's last step POSTs `/api/revalidate?tags=…` with the secret in an **`x-revalidate-secret` header** (never the query string — that leaks it into Vercel/proxy logs; `REVALIDATE_SECRET`, set in both Vercel env and GitHub secrets), which expires the tags so the next view refetches. New page reads that hit pipeline-written tables should go through this lib and reuse the tags. A browser reload does NOT bypass the cache.
  - **Vercel drops any cache entry > 2 MB silently** — it isn't cached and nothing warns you; the page then refetches from Supabase on every request. Keep each cached unit well under 2 MB (Signal Pro caches the universe in fixed 400-row chunks, ~0.57 MB each, for exactly this reason) and measure the JSON size before caching a large read.
  - Functions are pinned to `hnd1` (Tokyo) in `dashboard/vercel.json` to co-locate with Supabase (`ap-northeast-1`); the default `iad1` (US East) crossed the Pacific on every DB round trip. Keep these in sync if the Supabase region ever changes. `x-vercel-id: <edge>::<function-region>` shows where a request actually ran.
  - Canonical host is **`www.loctinhieu.com`**; the apex 308-redirects, so any `curl`/webhook POST must use `www` (or `-L`).
  - Tags: `ta-data`, `fa-data`, `macro-data` (pipeline-written) plus `rec-data` (recommendations/daily_logs) and `feedback-data`. The last two are also written *by the app*, so `/api/recommendations/manual` (BUY/SELL), `/api/push`, `/api/fa-import` and `/api/feedback` call `revalidateTag(...)` directly — a mutation must always invalidate its tag or the page will serve a stale write.
  - **Any Supabase read that could exceed 1000 rows must page** — via `fetchAllPaged` in the dashboard, `ta.common.paged_select` in Python. PostgREST silently truncates at 1000, and with an ASC order that drops the *newest* rows. This broke the Analysis default-indicator selection once (a symbol has >1000 triggered signals). Pages need a deterministic tie-break column in the `order` too, or page boundaries can duplicate/skip rows.
  - **`compute_ta_signals.load_ohlcv` was the one unpaged read that grows without bound (fixed 2026-09-01).** It has no date filter by design — every indicator computes over the whole series — so it scales with each symbol's history, and it is called per symbol in the daily pass. Ordered ASC, the cap drops the NEWEST bars, so past 1000 it would have returned a clean-looking DataFrame that stopped before the present and computed today's signals from years-old data, with no exception and no warning. The deepest symbol holds ~604 bars, so nothing in the live data could surface it — **it would have arrived silently with the first deeper OHLCV backfill**, which is exactly what the Silver-tier full-history backfill would do. Pinned by `scripts/tests/test_paged_ohlcv.py`, whose stub reproduces the server's silent cap. Swept the rest of the Python reads at the same time: `ta/adjustments.py` was already paged; `catalyst.py` (240d), `benchmark.py` (400d) are date-bounded; `ta_score.py`/`rs_rating.py`/`catalyst.py`'s universe reads are paged or chunked by `.in_()` of 200; `sr.py`/`trendlines.py` return a handful of rows per symbol.
- **`ta_signals` stores ONLY triggered rows (2026-09-02).** An indicator writes one row per symbol per day carrying both the yes/no (`triggered`) and the number it measured (`value`); the "no" answers were 82% of the table (46,711 rows on 2026-08-28, 8,597 triggered) and **nothing has ever read them** — all three readers filter `triggered = true` (`scanner/page.tsx`, `api/scanner/route.ts`, `chart-payload.ts`), and a sweep found no view or function over the table. They cost ~2 GB/yr for an archive no query touched; the value stays recomputable from `ta_ohlcv`, which is the source of record. **Measured on the live table (pruned 2026-09-02): 1,284 MB → 159 MB**, i.e. 7,327,701 → 1,599,754 rows and 1.1 GB freed. The saving beat the estimate because **INDEXES were 58% of the table** (739 MB of 1,284) and btrees reclaim space worst — they fell 90% against the heap's 85%. Per row: 184 B before (bloated), **104 B freshly packed**, against a 150 B paper estimate that assumed no bloat — so growth is now ~824 KB/session, ~210 MB/yr, down from ~2.04 GB/yr. Migration **056** prunes the history (resumable — it commits per date, because one delete over ~6M rows exceeds the statement timeout that a bare `count(*)` on this table already hits; a plain `DELETE` also does not shrink the disk, only `VACUUM FULL` does).
  - **Dropping the false rows without DELETE-THEN-INSERT is the bug, not the saving.** The plain upsert it replaced kept history honest by OVERWRITING a stale `triggered = true` with the `false` a recomputation produced. With false rows no longer written that repair disappears, so a re-run (`--since`, `--all-dates`, or a resweep after `refresh_adjustments.py` re-backfills a corporate action and changes what those bars trigger) would leave the old true row standing forever — a signal the scanner still lists and the chart still marks for a bar that no longer produces it. `write_signals` therefore clears the `(symbol, date)` span first, taking the span from the rows **before** the triggered filter, since a symbol-date whose signals all turned false has nothing left to name the date. Empty input issues no delete, so an indicator crash cannot erase a symbol's stored signals. Pinned by `scripts/tests/test_signal_write.py`.
  - **The count gates were checked before shipping and do not move:** `st.require("Step 2 signals", …, minimum=1)` is a flat floor, not proportional, and `audit_data.layer_signals` tests freshness plus zero-count only — an 82% drop trips neither. `total_signals` now counts rows STORED (so `ta_runs.signals_written` falls ~68k → ~8.6k a night); `total_evaluated` reports what was computed.
- Migrations are append-only and applied manually; add the next numbered file rather than editing an applied one.
- **Writes need the service-role key.** Migration 045 revoked anon's write access: the anon key ships inside the client JS bundle, so `for all using (true)` let anyone rewrite the dataset through PostgREST (demonstrated 2026-08-10 — one unauthenticated PATCH overwrote all 1,902 `fx_central_rate` rows). Python resolves the key via `ta.common.resolve_supabase_key()` (service role, else a loud anon fallback); the dashboard writes through `src/lib/supabase-admin.ts`. The service key must never be `NEXT_PUBLIC_*`, never reach a client component, and never go in a query string. **A denied PostgREST write returns 204 with zero rows affected, not an error** — so a writer missing the key looks like it succeeded. That is why the fallback warns loudly and the workflows emit a `::warning::`.
